### 2b. Beam clamp — half-wrap U + `_CLAMPING_CLEARANCE`  (block (c), ~line 1586)
`_CLAMP_CUTOUT` was **renamed** `_CLAMPING_CLEARANCE = 1.0` (top of file, ~line 109). It drives BOTH the
U-notch clearance AND the plate↔clamp gap ("almost kiss, don't touch"). Shared clamp geometry is hoisted
**above** the plate block so both reuse it: `_CLAMP_X0, _CLAMP_LEN, _CLAMP_ARM = 54, 38, 15` and

### 2c. Mid plate (`Side_Plate_Left`) — reliefs + a 4 mm shell raise  (block (a), ~line 1555)
Two front reliefs so the beam/clamp don't interpenetrate the plate: a **recess** to `arm_tip+clearance`
over the clamp Z-band, and a **through-slot** (beam+clearance) for `Lower`'s rear half. Then the
"Moving gantrybeams" fix: **`PLATE_DZ = 4.0` — translate the imported BODY shell UP 4 mm BEFORE the bores
/reliefs are cut** (`_shell = _read_shape(BODY); _shell.translate((0,0,4)); _body = _xbore(_shell, …)`).
This raises the plate's ledges to rest against the front-clamp bottom (`Edge15↔Edge8`, world Z127) and the
`Upper1` beam bottom (`Edge10↔Edge5`, world Z132), while every bore/relief — cut at fixed **local** Z —
stays put at its world position. **Why the shell, not the placement:** `TIE_ZL` (local Z of the tie bore)
is SHARED with the beam clamp, so moving the plate's `_place` z would break the tie line. Raising only the
imported shell sidesteps that. Verified: plate ledge now at Z127.0 (=front clamp) and Z132.3 (≈beam; 0.3 mm
press — a rigid raise can't make both exact, the two ledges are 5.3 mm apart vs 5.0 mm targets, I chose
`4.0` so the front-clamp contact is exact and #2 is a hair of press not a gap).

### 2d. Front clamp (`Side_Plate_Front_Clamp`, imported M20cd clips) — relieved U-outtakes (block (b))
Both U-outtakes are relieved to `beam + _CLAMPING_CLEARANCE` so each wraps its beam with a clean 1 mm gap
(root cause of the old overlaps: the imported U floors sat *above* the beam bottoms, so each beam's lower
half poked into solid clamp). **Frame map:** the front clamp is placed at `z = 93 + CLAMP_DZ` (=`_fz`=96.5),
so a world beam Z maps to the LOCAL `front` shape via `local_Z = world_Z − _fz`; the cut is done on the
LOCAL `front` shape (before `add_shape_obj`) with **full Y**, so BOTH the L copy and the mirrored `_R` get
it. The relief loop is `for _bz0 in (GZ_LOW, GZ_HIGH): front = front.cut(box at (_bz0 − _cc/2) − _fz)`.
**The top block is KEPT** (do NOT re-add a top trim): I earlier trimmed the overhang and it turned the
upper outtake into an **L**; the user wanted the block back, so the imported top arm stays and the upper
outtake is a **U** again (front clamp Z back to 286.5).

Numeric state after all of the above: `Lower ∩ MidPlate = 0`, `Upper1/Upper2 ∩ FrontClamp (& _R) = 0`,

## 3. Gotchas learned / reinforced this session
- **`obj.Shape` is in WORLD coords** (the `_place` Placement is composed into what `.Shape` returns), so
  `Shape.common()` between two objects is a valid world-frame overlap test, and `Shape.BoundBox` reads
  world. But when you **cut a shape before `add_shape_obj`**, you're in that shape's LOCAL frame — map with
  the placement (`local = world − place`). Mid plate place z=93; front clamp place z=93+CLAMP_DZ=96.5.
- **Relieve/raise via the LOCAL pre-placement shape, cut features at FIXED local Z**, so a shape shift does
  NOT drag its holes/reliefs (that's how the 4 mm plate raise kept the tie line — §2c).
- **Verify by `Shape.common(other).Volume`** (0 = clean fit / touching; a few hundred mm³ over an 800 mm
  beam = a sub-mm² sliver = "contact/press", visually fine). Bounding-box overlap alone is misleading —
  two parts can share a bbox with zero shared solid.
- **Cut the shared L shape once, full-Y, to relieve both L and `_R`** (the `_R` is just a Y-mirror + place).
- `:0` display sleeps → GUI screenshots fail silently. Fall back to numeric verification.
- Everything in handover 7 §2 still holds (`Vector.multiply` mutates; `removeSplitter`; coord frame; etc.).
